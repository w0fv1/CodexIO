# Codexio

Codexio 是一个运行在 Windows 本机的消息中转工具。它适合把本机的 AI 助手、网页对话入口、飞书会话和邮件收发连接在一起，让你可以用一个稳定的本地入口处理多种消息来源。

安装完成后，Codexio 会在电脑后台运行，并在系统托盘显示图标。你可以通过双击托盘图标打开本机对话页面，也可以让其他工具通过本机地址接入它。Codexio 不依赖远程数据库，主要配置、运行状态和日志都保存在本机。

## 适合谁使用

Codexio 适合这些场景：

- 你希望在本机长期运行一个轻量消息中转入口
- 你希望把网页对话、飞书消息或邮件消息接到同一套处理流程
- 你需要一个可以随电脑启动、可以在托盘里管理的桌面工具
- 你不希望把日常对话记录默认保存到远程数据库
- 你需要在本机工作区里配合 Coding Agent 或其他自动化工具使用

如果你只是偶尔打开一个网页聊天窗口，不需要飞书、邮件或本机长期驻留能力，Codexio 可能不是必须的。但如果你希望把多个入口合成一个稳定的本地通道，它会更合适。

## 下载与安装

发布页通常会提供 Windows 安装器。下载后直接运行安装器，按提示完成安装即可。

安装时可以选择安装位置。默认情况下，卸载或升级不会删除已有配置和运行数据，这样你重新安装后仍能继续使用原来的配置。

安装完成后，你可以在开始菜单或桌面快捷方式中启动 Codexio。启动成功后，系统托盘会出现 Codexio 图标。如果你没有看到主窗口，这是正常的，Codexio 主要以托盘应用的方式运行。

## 首次启动

首次启动后，建议按下面顺序确认：

1. 查看系统托盘是否出现 Codexio 图标
2. 双击托盘图标，确认浏览器能打开本机对话页面
3. 在页面中发送一条测试消息，确认页面可以正常显示
4. 如果你要接入飞书或邮件，再进入对应配置

Codexio 首次启动会自动准备必要的本机配置。你不需要手动创建数据库，也不需要单独启动服务进程。

## 日常使用方式

### 容器运行

Codexio 可以作为无桌面容器服务运行。容器模式适合部署在一台固定机器上，对外暴露 Web 页面和 WebSocket 通道。容器内环境按独立机器使用，镜像内自带 Node、构建工具和 Codex 运行环境，Codex 登录态、配置、日志和工作区都保存在容器卷，不依赖宿主机的 Codex CLI 或 `~/.codex`。

容器入口文件：

```bash
cd app/_sub/codexio
cp container/.env.example container/.env
podman-compose --env-file container/.env up -d --build
```

启动后访问：

```text
http://127.0.0.1:8787
ws://127.0.0.1:8787/ws
```

Linux Podman 默认使用 host network。这样容器内可以访问宿主机 `127.0.0.1:7890` 代理，外部也可以直接访问 `127.0.0.1:8787`。数据、配置和工作区仍通过 named volume 与宿主隔离。需要修改服务端口时，改 `/data/config.yaml` 的 `server.port`，不要在 compose 里维护第二套端口配置。

容器默认使用两个 named volume：

| Volume | 容器路径 | 内容 |
| --- | --- | --- |
| `codexio-data` | `/data` | 配置、日志、上传文件、运行状态、Codex 登录态 |
| `codexio-workspace` | `/workspace` | Codex 执行任务的工作目录 |

首次启动时，镜像会把 `container/config.yaml` 复制到 `/data/config.yaml`。默认只启用 Web 输入、Web 输出和 Codex Agent，不启用飞书、邮件和 nfirco 线程通道。`server.host` 必须保持 `0.0.0.0`，否则容器外无法访问。`server.token` 默认从 `CODEXIO_SERVER_TOKEN` 读取，用于管理 API，例如停止服务。

容器内 Codex 以 root 身份运行。这样 Codex 可以在容器里安装系统包、修改容器文件系统、拉取源码、构建项目和写入 `/workspace`。宿主机不挂载到容器内，文件需要通过 Codexio 文件接口、Web 页面下载、`podman cp` 或专门新增的 volume 显式进出。

查看当前配置：

```bash
podman exec codexio cat /data/config.yaml
```

修改配置：

```bash
podman cp codexio:/data/config.yaml .tmp/codexio-container-config.yaml
vim .tmp/codexio-container-config.yaml
podman cp .tmp/codexio-container-config.yaml codexio:/data/config.yaml
podman restart codexio
```

容器默认使用镜像内置的 Codex 运行环境：

```yaml
agents:
  echo:
    enabled: false
  codex:
    enabled: true
    bundled: true
app:
  workspace:
    path: /workspace
    perIoThread: true
```

首次使用 Codex 时，如果容器内还没有登录态，Web 页面会返回登录地址和验证码。按提示完成登录后，登录态会保存在 `codexio-data` volume 的 `/data/codex`，重启容器不会丢失。

容器默认按 Linux host network 的宿主本机代理配置出网代理：

```yaml
proxy:
  enabled: true
  host: 127.0.0.1
  port: 7890
  noProxy: localhost,127.0.0.1,::1
```

如果宿主机代理不是 `7890`，修改 `/data/config.yaml` 后重启容器。如果不需要代理，把 `proxy.enabled` 改为 `false`。如果未来改成桥接网络，不要继续使用 `127.0.0.1` 指向宿主代理，应改为容器网络可访问的代理地址，例如 `host.containers.internal` 或一个明确暴露的局域网地址。

如果需要让外部程序直接发消息，连接 WebSocket 后发送：

```json
{"type":"thread.create","requestId":"request-1"}
```

服务端会返回 `thread.created`，其中 `thread.id` 是服务端签发的 Web 会话 ID。随后使用该 ID 发消息：

```json
{"type":"message.send","webThreadId":"服务端返回的ID","sourceMessageId":"调用方生成的消息ID","text":"你好","files":[]}
```

同一个连接会收到 `ready`、`thread.created`、`history`、`threads` 和 `message` 事件。`message.role` 为 `agent` 时就是 Codex 回复。

从外部向容器传文件可以使用 Web 页面上传，也可以调用文件接口：

```bash
curl -F file=@./local-file.txt http://127.0.0.1:8787/api/files
```

接口会返回文件 ID。把这个 ID 放到 WebSocket 消息的 `files` 数组里，Codexio 会把文件写入当前线程工作区。Codex 在容器内生成文件时，应把结果保存到 `/workspace` 或当前线程目录，并在回复里用 Markdown 链接引用真实文件路径，Web 页面会把文件作为可下载内容展示。

Codexio 对所有通道使用同一个文件模型。输入通道先把平台资源下载到 Codexio 文件目录，再把本地文件放入消息的 `files`。Agent 输出先进入 AgentManager；AgentManager 统一解析 Markdown 链接和图片、导入本地或远程文件并生成 `files`，之后输出通道只负责把本地文件发送到目标平台。

需要直接从容器复制文件到宿主机时使用：

```bash
podman cp codexio:/workspace/output.zip ./output.zip
```

需要从宿主机导入目录到容器工作区时使用：

```bash
podman cp ./project codexio:/workspace/project
```

如果需要长期挂载某个外部目录，应在 `compose.yaml` 中新增明确 volume，不要挂载宿主机家目录或 Codex 配置目录。

管理 API 停止容器内服务：

```bash
curl -X POST -H "Authorization: Bearer $CODEXIO_SERVER_TOKEN" http://127.0.0.1:8787/api/server/stop
```

容器模式不建议挂载宿主机 `~/.codex` 或宿主机 Codex 命令。这样可以避免宿主机个人配置、PATH、登录态和升级节奏影响容器服务。

### 打开对话页面

双击系统托盘中的 Codexio 图标，会使用默认浏览器打开本机对话页面。

这个页面是最直接的使用入口。你可以在这里发送消息、观察通道状态，也可以把它当作本机消息调试面板。

### 后台运行

关闭浏览器页面不会退出 Codexio。只要托盘图标还在，Codexio 仍然在后台运行。

如果你希望完全退出，请在托盘图标菜单中选择退出。直接关闭浏览器标签页只会关闭页面，不会关闭后台服务。

### 开机启动

Windows 桌面安装版可以在配置页的 App 分组中勾选“开机启动”。保存后立即生效，取消勾选会移除开机启动项。开发模式、命令行模式和容器模式不会修改 Windows 开机启动项。

### 阻止系统睡眠

桌面版默认在 Codexio 运行期间阻止系统自动进入睡眠，保证后台 Agent 和消息通道持续运行，但不会阻止屏幕自动关闭。可在配置页的 App 分组中取消勾选“阻止系统睡眠”，保存后立即生效。命令行模式和容器模式不会修改系统电源状态。

### Codex 授权与对话隔离

关闭 Bundled、使用外部 Codex 时，Codexio 复用用户现有的 Codex 登录授权，不要求重复登录。

Codexio 只创建和维护自己发起的对话 thread，不扫描、导入或同步 VS Code 及其他 Codex Client 的对话记录。其他客户端的对话不会出现在 Codexio 的 Web 页面或输出通道中。

### 更新版本

安装新版本前，建议先退出正在运行的 Codexio。安装器默认会保留已有配置。升级后重新启动即可继续使用。

如果新版本包含配置结构调整，Codexio 会尽量沿用已有配置。升级后建议打开页面发送一条测试消息，确认通道仍然正常。

从 `0.14.1` 开始，Codexio 不再限制 Codex 单轮任务的执行时长。长时间运行的任务会持续执行，直到 Codex 自身完成、失败，或用户主动停止。

从 `0.15.0` 开始，Codexio 桌面版默认阻止系统自动睡眠，以保持 Agent 和消息通道运行；屏幕仍可自动关闭，也可在 App 配置中关闭该功能。

从 `0.16.0` 开始，Codexio 使用本机 SQLite 统一持久化 Web、外部通道与 Agent thread 的身份映射和会话元数据。重启和升级后会恢复 Web 会话列表与标题；重新绑定飞书群聊会退休旧群会话，新群中的新会话使用全新映射。

从 `0.16.1` 开始，Codexio 检查登录状态时不再主动刷新 Codex 登录令牌。

## 可连接的消息入口

Codexio 可以按需启用不同入口。你不需要一次配置所有入口，只启用当前需要的即可。

### Web 页面

Web 页面是默认入口，适合本机直接使用和基础测试。

建议先确认 Web 页面工作正常，再配置飞书或邮件。这样排查问题时可以先确定 Codexio 本身是否正常运行。

### 飞书

如果你希望在飞书里收发消息，可以配置飞书开放平台应用或飞书机器人。

飞书接入适合这些情况：

- 团队成员习惯在飞书中发起消息
- 需要把群聊或私聊里的消息交给本机处理
- 希望把处理结果回传到同一个飞书会话

首次接入飞书时，建议先在目标会话里发送一条简单测试消息，确认 Codexio 已识别当前会话。一个飞书通道通常绑定一个明确的群聊或私聊，避免多个会话混在一起导致消息归属不清。

重新绑定到另一个群聊后，旧群聊已经建立的会话会被退休，不会转发到新群；新群中的新会话会建立新的映射。

飞书输入支持文字、富文本、图片、文件、音频和视频资源。资源会先下载到 Codexio，再和消息一起进入统一处理链。群聊配置 `aite: false` 时，`allowedOpenIds` 中的用户可以发送不带 @ 的纯附件消息；`aite: true` 时群聊消息仍需明确提及机器人。

### 飞书 Webhook

飞书 Webhook 适合只需要把结果发到飞书，不需要从飞书接收消息的场景。

例如，你只希望把某些处理结果通知到一个群里，可以使用 Webhook。它更简单，但能力也更单向。

### 邮件

邮件通道适合把指定邮箱中的来信转为输入，并通过 SMTP 发出回复。

使用邮件通道时，请注意：

- 建议使用专门邮箱，不要直接绑定私人主邮箱
- 建议只允许可信发件人触发处理
- 邮箱密码或授权码应妥善保存
- 首次配置后先用一封测试邮件验证收发链路

邮件通道只适合清晰、低频、可追踪的消息流。如果你需要高频实时对话，建议优先使用 Web 页面或飞书。

## 配置建议

Codexio 的配置保存在本机。正常使用时，你通常不需要频繁修改配置文件。

建议遵循这些原则：

- 先启用最少入口，确认正常后再逐步增加
- 一个入口只绑定一个明确用途
- 不要把测试通道和正式通道混在一起
- 修改配置前先退出 Codexio
- 修改后重新启动，并发送测试消息确认结果

如果你不确定某个配置项的含义，不要直接复制来源不明的配置。优先从最小可用配置开始。

## 数据与隐私

Codexio 默认不把对话记录保存到远程数据库。它在本机数据目录的 `state/thread-identity.sqlite3` 中持久化 Web、飞书、邮件、Nfirco 与 Agent thread 的统一身份映射及会话标题。该文件位于安装包之外，桌面版升级和容器重启会继续使用同一份数据；容器部署必须保留 `/data` volume。

Web 页面重连或 Codexio 重启后会恢复会话列表、标题和映射，但不会恢复消息正文。消息正文仍只保存在当前进程内存中。

仍然需要注意：

- 你发送到飞书、邮件或其他外部通道的内容，会进入对应平台
- 本机配置可能包含令牌、邮箱授权码或 Webhook 地址
- 不要把配置文件发给无关人员
- 共享电脑上使用时，建议确认系统账号和磁盘权限

如果你要处理敏感信息，建议先确认所有外部通道的权限、日志和保留策略。

## 常见操作

### 导出当天日志

点击托盘菜单中的“日志”，Codexio 会打开日志目录，将点击时的当天日志保存到 Downloads，并把同一份日志内容复制到剪贴板，便于直接粘贴到排障会话中。

### 打开页面后没有消息

先确认托盘图标仍在。然后刷新浏览器页面，再发送一条新的测试消息。

如果页面恢复了会话列表但没有历史消息正文，这是正常的。Codexio 持久化会话元数据和身份映射，不把消息正文当作长期消息库。

### 飞书没有响应

按顺序检查：

1. Codexio 是否正在运行
2. 飞书应用或机器人是否启用
3. 当前会话是否已经完成绑定
4. 飞书侧权限是否允许接收和发送消息
5. 是否把消息发到了正确的群聊或私聊

如果刚修改过飞书配置，建议退出并重新启动 Codexio。

### 邮件没有被处理

按顺序检查：

1. 邮箱地址和授权码是否正确
2. 发件人是否在允许范围内
3. 邮件是否进入了配置的收件箱
4. 邮件是否已经被标记为已读
5. 邮箱服务商是否限制了 IMAP 或 SMTP

很多邮箱需要单独开启 IMAP/SMTP，并使用授权码而不是登录密码。

### 托盘图标还在，但页面打不开

可以先退出 Codexio，再重新启动。

如果仍然打不开，可能是本机端口被其他程序占用，或者安全软件拦截了本机服务。此时可以查看日志，确认启动是否成功。

### 升级后配置不符合预期

安装器默认保留配置。如果你希望彻底重新开始，可以先备份需要保留的信息，再在卸载时选择清理用户数据，或手动清理 Codexio 的本机数据目录。

不建议在不备份的情况下直接删除配置，尤其是已经配置过飞书、邮件或 Webhook 的环境。

## 使用建议

- 把 Codexio 当作本机消息入口，而不是长期知识库
- 重要结果应保存到你的正式工作系统中
- 飞书、邮件等外部通道先小范围试运行
- 每次升级后做一次 Web 页面测试和关键通道测试
- 不使用的通道及时关闭，减少误触发
